01● built

Mark 2000 — Self-Hosted VPN & Network Management Server

A multi-protocol VPN/proxy gateway on Ubuntu, with a management layer I built from scratch.

Xray-corePythonReactiptablesTCP BBR
Read the write-up

Objective

Build a self-hosted, privacy-focused VPN and multi-user proxy gateway on a spare Ubuntu laptop, with central management of users and devices — replacing an unreliable commercial VPN and enabling secure remote access to my own network.

Architecture

  • Core engine: Xray-core providing multiple inbounds — VLESS + REALITY (XTLS Vision), VLESS over WebSocket/gRPC, VMess, Trojan+TLS and Shadowsocks — for protocol flexibility and traffic obfuscation.
  • Management layer: a Python backend for user/device creation, config generation and monitoring, with a React dashboard front-end; Bash scripts automate deployment and generate per-device QR profiles and subscription links.
  • Performance tuning: TCP BBR congestion control with the fq queue discipline, tuned socket buffers and MTU/MSS clamping per path.
  • Perimeter: iptables rules restricting exposure and isolating user traffic; local proxies bound to 127.0.0.1.

What I learned

  • Orchestration is harder than the crypto: most failures came from services competing for the same ports and non-atomic config reloads, not from the VPN protocols themselves.
  • A security review of my own early scripts flagged real hazards to fix in any future build — a self-signed Trojan cert with allowInsecure=1, plaintext secrets in backups, and management UIs that must never be exposed to the public internet.

Status & honesty note

Working self-built project on my own hardware. Throughput and multi-user capacity figures are not independently benchmarked, and I'd re-engineer the identified weaknesses before treating it as production-grade.

02● write-up

Network Reconnaissance with Nmap

A full discovery-to-fingerprint workflow on my own network, with defensive takeaways.

NmapKaliRecon
Read the write-up

Objective

Carry out the reconnaissance phases of a security assessment against my own home network, moving from "what hosts exist?" to "what is this host and what does it run?".

Method

  • Host discovery: nmap -sn 192.168.0.0/24 — a ping sweep with no port scan, mapping the live footprint quietly.
  • Service enumeration: nmap -sV against a target host, exporting to XML.
  • OS detection: sudo nmap -O for fingerprinting.
  • Aggressive pass: sudo nmap -A combining version/OS detection, default NSE scripts and traceroute.

Findings

  • Six live hosts, including the gateway and an Apple device exposing only ports 49152 and 62078 (the iphone-sync service gave the device type away before any OS scan).
  • OS detection returned slightly different guesses between the -O and -A runs — a genuine lesson in the limits of fingerprinting a hardened device with a small exposed surface.

Defensive takeaways

  • Minimise attack surface — every closed/filtered port is one less thing an attacker learns.
  • Reconnaissance is noisy: ping sweeps and sequential probes are detectable with IDS/IPS and firewall logging.
  • Segment the network so a single foothold reaches as little as possible.
03● write-up

Vulnerability Assessment & Exploit Validation

Nessus → investigation → authorised Metasploit validation → remediation, on a deliberately vulnerable lab host.

NessusMetasploitReporting
Read the write-up

Objective

Run a full assessment workflow against an intentionally vulnerable Metasploitable 2 host in an isolated lab — discovery, investigation of a finding, controlled validation, and remediation.

Method & findings

  • Discovery: a Tenable Nessus credentialed scan surfaced numerous findings; I focused on the FTP service, identified as vsftpd 2.3.4 (plugin 52703).
  • Investigation: that exact release carries a well-documented backdoor introduced into its distribution in 2011 — CVE-2011-2523 — a classic software supply-chain compromise.
  • Validation: the matching Metasploit module (exploit/unix/ftp/vsftpd_234_backdoor, rank excellent) confirmed the finding was a true positive and returned a shell.
  • Proof: verified root-level access on the target (hostname, id, /etc/passwd), then stopped — no destructive actions.

Remediation recommended

  • Remove/upgrade the backdoored vsftpd build immediately; install only from trusted repositories with checksum/signature verification.
  • Prefer SFTP/FTPS over plain FTP; decommission the other legacy clear-text services (Telnet, rlogin, rsh) the scan surfaced.
  • Establish ongoing vulnerability management — regular authenticated scans and a patch cadence.

05● lab

Wireless Network Security Auditing Lab

Authorised WPA/WPA2 auditing with Wifite and the aircrack-ng suite, plus blue-team fixes.

Wifiteaircrack-nghashcatWPS / PMKIDWPA3
Read the write-up

Objective

Assess the security posture of WPA/WPA2 wireless networks in an authorised lab — evaluating pre-shared-key strength, WPS configuration and management-frame protection.

Method

  • Identified the wireless NIC, killed interfering daemons (airmon-ng check kill) and enabled monitor mode.
  • Enumerated BSSIDs, channels, encryption and connected clients with wifite.
  • Captured clientless RSN PMKIDs and full 4-way EAPOL handshakes (via targeted deauthentication).
  • Tested WPS Pixie-Dust / PIN resistance on legacy routers.
  • Audited captured .cap/.22000 material offline with aircrack-ng/hashcat against wordlists.

Blue-team remediations

  • Disable WPS entirely (defeats Pixie-Dust and PIN brute force).
  • Enable 802.11w management-frame protection to mitigate forged deauth attacks.
  • Move from WPA2-PSK to WPA3-SAE, or 802.1X/RADIUS, and enforce 16+ character passphrases.
