PROJECT / 01Running · self-reported

JAT Cipherline 2300 — Self-Hosted VPN Gateway & Home Lab

A Proxmox home lab in Bangladesh that I run from Cardiff: a multi-protocol VPN for my family, private cloud storage and a password manager, a Kali VM, and one web console that manages all of it.

Proxmox VEUbuntuWireGuardAmneziaWGOpenVPNXray-coreHysteria2TailscaleDocker
Read the case study

What it is

  • Five virtual machines on one HP mini PC running Proxmox VE: the VPN gateway, Kali Linux with the Wi-Fi card passed through for wireless labs, a Wazuh SOC, a services VM, and Splunk, started only when needed.
  • VPN: WireGuard, AmneziaWG, OpenVPN, the Xray protocols (VLESS, VMess, Trojan, Shadowsocks) and Hysteria2. Each person has their own account and devices, with a per-person switch for access to the home network.
  • Services: Nextcloud for family files, Vaultwarden for passwords and Pi-hole for DNS filtering, behind Traefik with a wildcard Let’s Encrypt certificate. They are reachable only at home, over the VPN, or from my own devices over Tailscale.
  • One master console: accounts with TOTP and passkey sign-in, an audit log, live latency and packet-loss charts, and lab controls (start, stop and back up VMs, apply updates, memory savers).

Security decisions

  • No administration interface (Proxmox, SSH, the console) is exposed to the internet; remote management goes over Tailscale.
  • Least privilege: the console reaches each machine through an SSH key locked to a fixed list of jobs with checked arguments, never a shell. Secrets travel on standard input, never on command lines or in logs, and services run in systemd sandboxes.
  • Change discipline: every change is proposed, approved and reversible, and work elsewhere never interrupts the running VPN.

Evidence & limits

  • Deployed in November 2026 and in daily use. The evidence is my own console screenshots and logs; it has had no independent audit or penetration test.
  • Built with AI-assisted engineering: I set the requirements, security rules and acceptance tests, and I deploy, test and operate every release on the real hardware. Much of the code was written with an AI coding assistant.
  • Nearly 500 automated checks run against stand-in machines before each release.
  • Addresses, endpoints, configurations and user data are deliberately not published.
PROJECT / 02Running lab

Home SOC — Wazuh, Splunk & Custom Detections

Every machine in the lab reports to a Wazuh SIEM. Alerts and raw events go to Splunk dashboards, with my own detections for the VPN, the console, the router and the services.

WazuhSplunkSuricataDetection engineeringLog analysisPython
Read the case study

What it does

  • A Wazuh 4.14 manager with agents on the Proxmox host and the lab’s VMs.
  • Custom decoders and rules for VPN sessions, console sign-ins, firewall blocks, Pi-hole summaries, refused web requests, Vaultwarden and the home router. After every install, a sample of each kind is replayed through Wazuh’s rule tester as a self-test.
  • Alerts go to Splunk, along with every raw event under a daily cap that follows the Splunk licence. Splunk has its own VM, started on demand to save memory.
  • Suricata IDS on the VPN gateway’s home-network interface with the ET Open rules (built and tested; currently switched off).

Findings & fixes

  • The self-test caught a silent detection gap: Wazuh tries top-level rules highest level first, so its generic “authentication failure” rule claimed the router’s “Login failed” lines before my router rule could. I restructured the router rules under a higher-level parent so they match first.
  • Alert noise: the VPN gateway’s web-server logs (scanner traffic that all appears as 127.0.0.1 behind the proxy) flooded the SOC, so I filtered them out at the agent so that real events stand out.
  • The TP-Link router has no remote syslog, only “Mail Log”. I added a small mail receiver on the SOC that accepts mail only from the router, never relays, skips lines it has already seen and passes new ones to Wazuh.

Evidence & limits

  • Home-lab scale: a handful of machines and family traffic. The detections are tuned by me and not independently validated.
  • The router fixes above were built and tested in November 2026 and are being rolled out.
  • Built with the same AI-assisted approach as the gateway; I run and tune it day to day.
